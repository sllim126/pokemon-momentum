Schedule at a glance (all times UTC)
------------------------------------

Everything below runs on its own. Systemd units are in `deploy/systemd/`; cron lines are in
adam's crontab (`crontab -l`), with a copy in `deploy/crontab.txt` (update it when the
crontab changes). Each job is explained further down in this file.

| When | Job | How it runs | Log |
| --- | --- | --- | --- |
| Daily 02:00 | Nightly market update: TCGCSV prices, metadata, snapshots, parquet, PriceCharting, indexes; restarts the app; Discord summary | `pokemon-momentum-daily-update.timer` | `logs/daily_update.log` |
| Daily 03:00 | Storefront market prices (`data/storefront/market_reference.json`, read by the new shop's product pages) | cron: `scripts/build_storefront_market_reference.py` | `logs/storefront_market_reference.log` |
| Daily 03:30 | Other games price archive (collect only) | `pokemon-momentum-tcgcsv-collect.timer` | see "Other games archive" |
| Daily 04:30 | Placeholder Library sync (new Mega-era sets and promos) | cron: `scripts/utilities/sync_placeholder_library.py` | `logs/placeholder_sync.log` |
| Daily 09:15 | Squarespace price sync (reaches the live store; retire when Squarespace closes 2026-11-14) | cron: `scripts/run_squarespace_price_sync.sh` | `logs/squarespace_price_sync_cron.log` |
| Daily 12:00 | TCGCSV catalogue crawl (sets and products for every game, at most 4,000 requests a day; Discord summary) | cron: `scripts/pipeline/run_tcgcsv_catalogue_host.sh` | `logs/tcgcsv_catalogue.log` |
| Daily 21:30 | TCGCSV archive backfill, from 2026-11-01 (one request a night while the archive is offline; downloads the gap when it returns; Discord summary) | cron: `scripts/pipeline/run_archive_backfill_host.sh` | `logs/archive_backfill.log` |

| Mon 11:00 | Weekly placeholder-name cleanup (product metadata + snapshot) | `pokemon-momentum-weekly-placeholder-refresh.timer` | journal |

Check timers with `systemctl list-timers | grep pokemon`.

Every cron job above runs through `scripts/monitoring/run_job.py`, and
`scripts/monitoring/collect_status.py` runs every minute; both feed Grafana (see Monitoring).

Monitoring (Grafana)
--------------------

Added 2026-11-05. Grafana shows the website, the jobs, the data downloads, this server, its
containers and the work list on four dashboards. Everything is free software on this host;
nothing is sent outside.

Open: http://192.168.1.240:3000 (LAN; sign in as `admin`). Folder "Pokemon Momentum":

- Overview (Grafana's home page): status tiles, "Did the jobs run?", data ages, trends
- Website: requests, errors and response times per app and route; outside probes
- Servers: CPU, memory, disks, network, updates, SMART, every Docker container
- Jobs & work: jobs, downloads, log files, docs/todo.txt, bug reports, git
- Home lab: the Proxmox cluster (3 nodes, every VM and container, storage pools)

How the numbers get there (Prometheus on localhost:9090 collects all of it):

| Source | What | Where |
| --- | --- | --- |
| node-exporter (:9100, apt) | host CPU, memory, disks, network, apt, SMART | already installed |
| `/metrics` on :8001 and :8010 | requests, errors, timings per route; price-data date | `scripts/dashboards/metrics.py`, `storefront/app/metrics.py` |
| blackbox exporter (127.0.0.1:9115, apt) | site up and response time, certificate expiry | `deploy/monitoring/prometheus_momentum.yml` |
| cAdvisor (127.0.0.1:8098, container) | per-container CPU, memory, restarts | `deploy/monitoring/docker-compose.yml` |
| `collect_status.py` (cron, every minute) | systemd job results, data download ages, logs, todo counts, bug reports, git | writes `/var/lib/prometheus/node-exporter/momentum_status.prom` |
| pve-exporter (127.0.0.1:9221, container) | Proxmox nodes, VMs, containers, storage (Home lab dashboard) | `deploy/monitoring/docker-compose.yml`; token and CA in `/etc/momentum-monitoring/` |
| `run_job.py` (wraps each cron job) | exit code, start/finish, duration, last success | writes `momentum_job_<name>.prom` in the same folder |

`/metrics` is private: it answers only requests from the host or Docker without proxy
headers, so through Caddy (market.poke6s.com/metrics) it is a 404.

Files in the repo: `deploy/monitoring/` (install script, Prometheus scrape jobs, Grafana
provisioning, the dashboard builder and its JSON output) and `scripts/monitoring/`.

Change a dashboard: edit `deploy/monitoring/build_dashboards.py`, then
`python3 deploy/monitoring/build_dashboards.py`; Grafana picks up the JSON within 30 s.
Edits made in the Grafana UI are lost at the next rebuild.

Add a job: add it to `JOBS` in `scripts/monitoring/collect_status.py` (with its interval).
A cron job also needs `/usr/bin/python3 scripts/monitoring/run_job.py <name> -- ` in front of
its command in the crontab and `deploy/crontab.txt`. A systemd job needs nothing else.

Install or repair (needs sudo; safe to rerun): `bash deploy/monitoring/install.sh`. It sets
the text-file folder to group `adam`, keeps the blackbox exporter on localhost, copies the
scrape jobs to `/etc/prometheus/momentum_scrape.yml` (loaded via `scrape_config_files` in
`prometheus.yml`, backup kept), installs the Grafana provisioning, sets the home dashboard
and starts cAdvisor. The crontab is separate: `crontab deploy/crontab.txt` (compare with
`crontab -l` first).

Checks:

```bash
curl -s 'localhost:9090/api/v1/targets?state=active' | grep -o '"health":"[a-z]*"' | sort | uniq -c
curl -s localhost:8001/metrics | head          # 200 from the host
curl -s -o /dev/null -w '%{http_code}\n' https://market.poke6s.com/metrics   # 404

```

Proxmox (added 2026-11-05): the pve-exporter container reads the Proxmox API at
https://192.168.1.75:8006 with API token `root@pam!grafana`. The token has privilege
separation on and only the PVEAuditor role on `/`, so it can read and change nothing. Never
untick privilege separation: on a root@pam token that would give full root. The token secret
is in `/etc/momentum-monitoring/secrets.env` (mode 600, outside the repo; names PVE_USER,
PVE_TOKEN_NAME, PVE_TOKEN_VALUE). HTTPS is verified against Proxmox's own CA, saved as
`/etc/momentum-monitoring/pve-root-ca.pem` (valid until 2032; SHA-256 fingerprint starts
C7:72:A8). If the Home lab tile "Exporter can read Proxmox" is DOWN: `docker logs
pve-exporter`; 401 = token wrong or deleted, 403 = permission missing, SSL error = the
Proxmox CA changed (fetch it again from Datacenter > node > System > Certificates).
To revoke: delete the token in Proxmox (Datacenter > Permissions > API Tokens).

Notes: the UniFi and training-server targets in `prometheus.yml` predate this and are down;
they are being replaced one at a time (docs/todo.txt). A job shows "No run recorded yet" until it has run
once under monitoring (systemd forgets runs at reboot; the weekly jobs fall back to the timer's
last trigger time). Overdue = no success for 1.5 x the job's interval plus an hour.

Store Pricing Ops
-----------------
The store pricing workflow now has three admin pages that work together:

- `/pricing-upload`
  - upload the latest Squarespace product export after you add or edit products
- `/supplier-pricing`
  - upload or OCR supplier screenshots and save reviewed JPY quote rows by SKU
- `/supplier-profitability`
  - compare latest supplier costs against market/store pricing with editable supplier-side and buyer-side assumptions

Daily price sync inputs:

- Squarespace export:
  - `/opt/pokemon-momentum/products_Apr-09_04-31-18PM.csv`
- Supplier quotes:
  - `/opt/pokemon-momentum/data/supplier_quotes.csv`
- Price rules:
  - `/opt/pokemon-momentum/data/store_price_rules.csv`
- Generated daily targets:
  - `/opt/pokemon-momentum/data/market_prices_latest.csv`

Important pricing behavior:

- the target builder uses `max(market_target, profit_floor)` for SKUs with supplier quotes
- `profit_floor` is derived from supplier cost plus landed-cost assumptions
- Japanese booster boxes use their own floor: landed cost (JPY at 159 per USD, 10% duty,
  shared inbound shipping, handling) plus 20%
- a Japanese rule whose latest supplier quote is more than 7 days old is priced at market
  + 25% instead
- rows without supplier quotes remain market-based
- these defaults can be changed with the environment variables at the top of
  `scripts/build_store_price_targets.py`
- `target_source` in `market_prices_latest.csv` says which price won: `market`,
  `profit_floor`, `jp_landed_markup`, or `jp_market_plus_25_stale_quote`

Retiring sold listings:

- `scripts/squarespace_retire_listings.py` hides a listing and sets its stock to 0 (the
  listing, photos and URL stay, so it is reversible; nothing is deleted)
- it looks up product and variant IDs in the latest Squarespace export, so upload a fresh
  export first if the listing is new
- always preview first, then apply:

```bash
python3 scripts/squarespace_retire_listings.py --sku 610540-holofoil --sku 84840
python3 scripts/squarespace_retire_listings.py --sku 610540-holofoil --sku 84840 --apply
```

- every change is logged to `output/squarespace_retired_listings.jsonl`
- to bring one back, make it visible and set its stock again in Squarespace

Recommended operator flow when adding a new SKU:

1. Add the product in Squarespace with a unique SKU.
2. Add or update its pricing rule in `data/store_price_rules.csv`.
3. Upload the refreshed Squarespace export on `/pricing-upload`.
4. Save the latest supplier quote on `/supplier-pricing` if you want profit-floor protection.
5. Review `/supplier-profitability` before allowing auto-pricing to move the SKU.

Storefront linking (`Poke6s` button)
------------------------------------

The dashboard can now show a `Poke6s` button beside `TCGplayer`, but only when the
current item is actually purchasable on the storefront.

Files involved:

- Squarespace export:
  - `products_Apr-09_04-31-18PM.csv`
- Store/TCGplayer mapping:
  - `data/squarespace_tcgplayer_mapping.csv`

Current link rules:

- the storefront button only appears when the latest Squarespace export says:
  - `Visible = Yes`
  - `Stock > 0` or `Stock = Unlimited`
- Japanese and English singles can resolve directly when:
  - Squarespace `SKU == TCGplayer product ID`
- sealed/store products resolve through:
  - `data/squarespace_tcgplayer_mapping.csv`
- one store SKU can map to multiple TCGplayer product ids by separating ids with `|`
  or `,` in `tcgplayer_product_id`

Recommended operator flow when a dashboard item should link to the storefront:

1. Confirm the Squarespace product is visible and in stock in the latest export.
2. If it is a single, confirm the store SKU matches the TCGplayer product id.
3. If it is a sealed/store product, add or update its row in `data/squarespace_tcgplayer_mapping.csv`.
4. Restart the app if the dashboard is still serving an older resolver path.

If the `Poke6s` button appears when it should not:

1. Check the selected `productId` in the dashboard URL or search payload.
2. Confirm whether that exact `productId` is mapped in `data/squarespace_tcgplayer_mapping.csv`.
3. Watch out for near-duplicate TCGplayer products:
  - sleeved pack vs unsleeved pack
  - art bundle vs standard pack bundle
  - ETB vs Pokemon Center ETB

If the `Poke6s` button is missing when it should appear:

1. Check the latest Squarespace export row for:
  - `Visible`
  - `Stock`
  - `Product URL`
2. Confirm the dashboard category matches the actual item market:
  - English -> category `3`
  - Japanese -> category `85`
3. For sealed products, confirm the exact TCGplayer product id is mapped to the store SKU.

What each page is expected to do
--------------------------------

`/pricing-upload`

- Purpose:
  - replace the local Squarespace export with a fresh one after store edits
- Inputs:
  - a valid Squarespace product CSV export
- Outputs:
  - archive copy in `data/archive/squarespace_exports/`
  - canonical working export in `products_Apr-09_04-31-18PM.csv`
  - coverage preview showing which SKUs have usable pricing rules
- Debug questions:
  - if a SKU is missing from automation, did it appear in the uploaded export?
  - if the export was accepted but no preview row appears, check `unmatched_rules`

`/supplier-pricing`

- Purpose:
  - convert supplier screenshots into structured SKU-linked quote rows
- Inputs:
  - OCR-reviewed rows containing supplier item name and JPY cost
- Outputs:
  - appended historical quote rows in `data/supplier_quotes.csv`
- Debug questions:
  - if OCR rows have blank SKU, check `data/supplier_name_mapping.csv`
  - if a quote was saved but not reflected later, confirm the SKU was populated on save

`/supplier-profitability`

- Purpose:
  - answer whether one unit is profitable under current supplier-side and buyer-side assumptions
- Inputs:
  - latest supplier quote per SKU
  - generated market/store target data
  - operator assumptions from the page
- Outputs:
  - per-unit rows with landed cost, break-even, target-margin price, and decision status
- Important interpretation:
  - results are per unit, not whole-order totals
  - `Estimate from Order` allocates whole-order shipping down to one box
  - `Manual per Item` ignores order shipping and uses only the manual inbound value

Generated target file fields
----------------------------

`data/market_prices_latest.csv` now includes:

- `market_price`
  - latest market price pulled from the signal snapshot
- `target_price`
  - final price the sync script will try to push to Squarespace
- `profit_floor_price`
  - minimum viable target derived from supplier economics, blank when no supplier quote exists
- `supplier_cost_jpy`
  - raw supplier quote used for floor calculation
- `target_source`
  - `market` when market logic won
  - `profit_floor` when supplier economics overrode the market target

If pricing looks wrong:

1. Check whether the SKU appears in `products_Apr-09_04-31-18PM.csv`.
2. Check its rule row in `data/store_price_rules.csv`.
3. Check its latest supplier quote in `data/supplier_quotes.csv`.
4. Rebuild targets:

```bash
cd /opt/pokemon-momentum
python3 scripts/build_store_price_targets.py
```

5. Inspect the resulting row in `data/market_prices_latest.csv`.

Pricing coverage audit:

```bash
cd /opt/pokemon-momentum
python3 scripts/utilities/audit_store_pricing_coverage.py
```

- `automated`
  - visible SKU is covered by the generated pricing target file
- `manual_expected`
  - visible SKU is intentionally manual, such as custom or print-on-demand items
- `hold_expected`
  - visible SKU is intentionally excluded until release or usable market data exists
- `missing_unexpected`
  - visible SKU is missing a rule or failed to generate a target and needs attention

Daily automation:

- the host-driven daily update now runs this audit once after the category pipelines finish
- if the audit finds `missing_unexpected` SKUs, the daily update log records a warning without failing the whole refresh

Normal daily operation
----------------------
The system is intended to run automatically.

Daily timer:

- `pokemon-momentum-daily-update.timer`

Daily service:

- `pokemon-momentum-daily-update.service`

Weekly full metadata refresh:

- `pokemon-momentum-weekly-refresh.timer`
- `pokemon-momentum-weekly-refresh.service`

Weekly placeholder cleanup refresh:

- `pokemon-momentum-weekly-placeholder-refresh.timer`
- `pokemon-momentum-weekly-placeholder-refresh.service`

Normal expectation:

- the daily run appends new price data
- refreshes metadata incrementally
- rebuilds snapshots
- exports new parquet partitions
- processes both category `3` (Pokemon) and category `85` (Pokemon Japanese) in sequence
- adds PriceCharting graded prices (English pass) and rebuilds the market-index snapshots
  after the parquet export
- restarts the app container afterward and posts a summary to Discord (see Alerts below)
- the weekly full metadata refresh runs Sunday at `11:00 UTC`
- the weekly placeholder cleanup runs Monday at `11:00 UTC`, 24 hours later
- the placeholder cleanup only reruns product metadata + product signal snapshot so stale
  `Product <id>` rows get another chance to resolve
- not to be confused with the Placeholder Library sync (printable binder placeholders):
  `scripts/utilities/sync_placeholder_library.py`, daily 04:30 UTC from adam's crontab, log
  `logs/placeholder_sync.log`. It adds new Mega-era sets and promos from the catalog and
  rebuilds the library; see `docs/tcg_placeholders_guide.md`

Backfill missing TCGCSV archive days
------------------------------------
TCGCSV's daily archive (`prices-YYYY-MM-DD.ppmd.7z`, every game, one file a day) went
offline on 2026-09-16. `data/raw` holds every file from 2024-02-08 to 2026-09-15.
`scripts/download/backfill_tcgcsv_archive.py` fetches the days after the newest file held,
once TCGCSV serves them again. It follows the TCGCSV rules (150 ms apart, stop on 403/429),
asks for each file at most once a day (`data/raw/backfill_attempts.json`), tests each file
with `7z t`, and extracts only days with no extracted folder yet (2026-09-16 to 10-07; later
days already came from the per-group fetch). The site can stay up: it doesn't touch DuckDB.

```bash
cd /opt/pokemon-momentum
sudo docker-compose exec -T pokemon-momentum python scripts/download/backfill_tcgcsv_archive.py --dry-run
sudo docker-compose exec -T pokemon-momentum python scripts/download/backfill_tcgcsv_archive.py
```

- It runs by itself every night at 21:30 UTC from 2026-11-01 (`run_archive_backfill_host.sh`,
  adam's crontab) and posts to Discord: grey "still offline" while TCGCSV answers 403 with its
  "temporarily removed" notice (one request a night, no ping), green with the list of days
  the night the archive returns, red with a ping on any other 403/429 or failure. Once the gap
  is filled it fetches the one new day each night and stays quiet unless something fails.
- Exit 3 with TCGCSV's "temporarily removed" notice: the archive is still offline. That
  was one request; the cron tries again the next night.
- After a successful run the next nightly update loads the new days into DuckDB for both
  English and Japanese. To load at once, stop the site and run the daily pipeline with
  `--skip-download` for categories 3 and 85 (below).

TCGCSV catalogue crawl (every game's sets and products)
-------------------------------------------------------
The archive files hold every game's prices but no names. `scripts/download/crawl_tcgcsv_catalogue.py`
saves TCGCSV's set lists and product lists for every game, as served, into
`data/tcgcsv_catalogue/` (`categories.json`, `<categoryId>/groups.json`,
`<categoryId>/<groupId>/products.json`; gitignored). Owner, 2026-11-02: download everything
we can within TCGCSV's rules.

- TCGCSV allows 10,000 requests a day for everything we run. The nightly Pokemon update and
  the other-games collector use about 2,000-4,000, so this job stops at 4,000 a day
  (`--budget`). The day's count is kept in `data/tcgcsv_catalogue/state.json`, so a second
  run the same day only uses what is left. The first full pass takes a few nights; after that
  each file is fetched again only once it is 30 days old (`--refresh-days`).
- Order: Pokemon, Pokemon Japan, Magic, Yu-Gi-Oh, One Piece, Lorcana, then every other game.
- Prices are not fetched here; they come from the archive.
- 404s are remembered and only asked again when due. A game whose first 25 product requests
  in a run are all 404 is skipped until it's due again (Marvel Comics: ~10,800 sets, none
  with product lists); the log says "Skipped games with no product lists: 69".
- It doesn't touch DuckDB, so the site can stay up.

```bash
cd /opt/pokemon-momentum
scripts/pipeline/run_tcgcsv_catalogue_host.sh          # tonight's slice, posts to Discord
sudo docker-compose exec -T pokemon-momentum python scripts/download/crawl_tcgcsv_catalogue.py --dry-run
```

- Schedule: daily 12:00 UTC from adam's crontab (`deploy/crontab.txt`). Discord: progress
  while the first pass runs, one post when it completes, nothing on a quiet night, red with
  a ping on 403/429 (exit 3: don't retry, check the TCGCSV Discord) or any failure.

Alerts (Discord)

including when they fail. The sender is `scripts/pipeline/notify_discord.py`, called from

What the colors mean:

- green: succeeded
- orange: finished, but needs a look (nightly: a market's newest price is more than 2 days
  old, or a step failed without stopping the run, such as the PriceCharting download, listed
  with its error line; price sync: some store updates were rejected)

After a power cut or reboot
---------------------------
What happens on its own: the nightly update's systemd timer has `Persistent=true`, so a
missed 02:00 run starts as soon as the machine is back. Since 2026-10-15 both nightly scripts
first wait up to 10 minutes for `tcgcsv.com` to resolve (at boot the network can be "up"
before DNS works; on 2026-10-15 the catch-up run failed on exactly that).

Check (the morning after):
- Discord: a green "Nightly market update" and "Other games price archive" for the day
- `curl -s localhost:8001/health?category_id=3` and `...=85`: `latest` should be yesterday

Check the public address too: the ISP can hand out a new public IP after a power cut
(2026-10-16). If `curl -s https://api.ipify.org` differs from `dig +short market.poke6s.com`,
update the `market` A record in Squarespace Domains (poke6s.com → DNS) to the new IP. The
site itself is fine meanwhile (`curl localhost:8001/health?category_id=3`).
To see what the internet sees, ask over HTTPS:
`curl -s "https://dns.google/resolve?name=market.poke6s.com&type=A"`. Plain `dig` from this
network, even `@ns-cloud-d1.googledomains.com`, is answered by a cache on the way out and keeps
showing the old IP until its TTL runs out (seen 2026-10-16).

If the update still failed or never ran:
- easiest: `sudo systemctl start pokemon-momentum-daily-update.service` (logs to
  `logs/daily_update.log`, posts to Discord). It only fetches TCGCSV's current day, so a
  day TCGCSV has already replaced can't be fetched later.
- the other-games archive: `scripts/pipeline/run_tcgcsv_collect_host.sh` (safe to repeat)
- the Squarespace price sync (09:15) is not re-run automatically. It changes live store
  prices, so run it by hand only if wanted: `scripts/run_squarespace_price_sync.sh`
  (`--dry-run` first to preview)

If the app is down
------------------
Symptoms:

- `/health` does not respond
- dashboard page does not load

Recovery:

```bash
cd /opt/pokemon-momentum
sudo docker-compose ps
sudo docker-compose logs --tail=200 pokemon-momentum
sudo docker-compose restart pokemon-momentum
```

If restart is not enough:

```bash
cd /opt/pokemon-momentum
sudo docker-compose up -d --build
```


If the latest date is stale
---------------------------
Symptoms:

- dashboard shows an older latest date than expected
- `/health` shows an older latest date

Likely causes:

- TCGCSV has not published a new day yet (the download exits 2, "older than 48h"), or is
  blocking us (exit 3, HTTP 403/429); the Discord alert quotes the error line
- daily pipeline has not finished
- parquet export did not run
- app restarted before the export stage completed

Checks:

```bash
tail -f /opt/pokemon-momentum/logs/daily_update.log
curl http://localhost:8001/health
```

What you want to see in the log:

- `Export parquet partitions`
- successful completion after that step

Manual recovery:

```bash
cd /opt/pokemon-momentum
sudo docker-compose run --rm pokemon-momentum bash -lc 'python scripts/utilities/export_parquet.py'
sudo docker-compose restart pokemon-momentum
curl http://localhost:8001/health
```


If the daily service fails immediately
-------------------------------------
Symptoms:

- `systemctl start pokemon-momentum-daily-update.service` fails fast

Checks:

```bash
sudo systemctl status pokemon-momentum-daily-update.service
sudo journalctl -xeu pokemon-momentum-daily-update.service
```

Common causes:

- bad service PATH
- script error in the pipeline
- Docker not available

Recovery:

- inspect the failing step in the journal
- fix the script/config problem
- rerun the service manually


If the pipeline appears stuck
----------------------------
Symptoms:

- `daily_update.log` stops advancing for a long time
- memory pressure spikes

Where this usually happens:

- the TCGCSV price download (one request per set, at least 150 ms apart, with retries on
  slow responses)
- metadata fetches from tcgcsv
- large price-load step

Checks:

```bash
tail -f /opt/pokemon-momentum/logs/daily_update.log
sudo docker stats
free -h
```

Notes:

- the daily path is now tuned to use a modest worker count
- one-time backfills are intentionally heavier
- metadata fetches can still be slow because they depend on tcgcsv responses

Recommended action:

- give the run time to finish if it is still advancing
- only intervene if logs are fully stationary and the process clearly failed or was OOM-killed


If DuckDB reports a file lock error
-----------------------------------
Symptoms:

- error about conflicting lock on `prices_db.duckdb`

Cause:

- the app container is running (it keeps the DB open for reading the whole time) while a
  write process tries to start

Normal design:

- the host wrapper stops the app before pipeline writes

Manual recovery:

```bash
cd /opt/pokemon-momentum
sudo docker-compose stop pokemon-momentum
sudo docker-compose run --rm pokemon-momentum bash -lc 'python scripts/pipeline/run_daily_update.py --skip-download --workers 4'
sudo docker-compose up -d pokemon-momentum
```

Standard recovery sequence
--------------------------
If something is wrong and you want the safest basic recovery path:

1. check `/health`
2. check `daily_update.log`
3. restart the app container
4. rerun the daily service manually
5. if latest date is still stale, run parquet export
6. if metadata is wrong, rerun metadata refresh
